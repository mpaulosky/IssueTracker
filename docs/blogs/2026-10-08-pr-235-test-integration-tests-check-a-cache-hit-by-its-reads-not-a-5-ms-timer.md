# test(Integration.Tests): Check a cache hit by its reads, not a 5 ms timer

- **Release tag:** `v0.0.42`
- **Source PR:** [#235](https://github.com/mpaulosky/IssueTracker/pull/235)

## PR description

### Why

`Cache_Performance_Meets_Baseline` in `tests/Integration.Tests/CacheIntegrationTests.cs` wrote one value, then timed a single `GetAsync` with a `Stopwatch` and asserted it took under 5 ms. That one call included JIT and first-use costs and was measured in wall-clock time, so it failed whenever the machine was busy: it measured exactly 5 ms at a load average of about 9 and blocked several pre-push gates.

The timing didn't test the service either. `CacheService` has no local layer of its own; it reads `IDistributedCache` on every call, and in this test that's an in-memory dictionary, so the read never leaves the process.

### What changed

- The test's in-memory distributed cache now counts its reads, writes and removals.
- The timing test is replaced by `GetAsync_With_Cached_Key_Should_Read_Distributed_Cache_Once_Test`. After a value is set, a `GetAsync` must return it with exactly one read of the distributed cache, no write and no removal, and log the hit. That would catch a hit that costs an extra round trip to Redis, which the timer was meant to catch, without depending on how loaded the machine is.
- No other test in the repo asserts on elapsed time.

### Verification

- `dotnet build tests/Integration.Tests -c Release -warnaserror`: no warnings.
- With a second `GetStringAsync` added to `CacheService.GetAsync` (not committed), the new test fails: `Expected distributedCache.ReadCount to be 1 ... but found 2`.
- With 24 busy-loop processes on a 24-core host (load average 35 to 46), `Integration.Tests` passed 10 runs in a row and then 6 runs at the same time, 11 of 11 tests each time.
- The pre-push gate passed.

Fixes #234
