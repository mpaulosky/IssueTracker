# fix(release): Wait for a just-published Release to be listed

- **Release tag:** `v0.0.21`
- **Source PR:** [#190](https://github.com/mpaulosky/IssueTracker/pull/190)

## PR description

### Summary

PR #188 was released as v0.0.20, but its run opened no blog PR. The `docs` job started 8 seconds after the Release was published, GitHub's release list didn't include it yet, and the job logged "Every Release already has its post on main; no blog PR needed" and succeeded. Re-running the `docs` job later opened #189, which confirms the cause.

- **`backfill_blog_posts.py --wait-for-prs`:** lists Releases again, every 5 seconds for up to a minute, until each named PR has one. A Release that never appears (its release failed) is logged as a warning, the posts that can be written are, and the next run picks up the rest, as before.
- **One listing:** the posts and the README and blog tables use the same listing, so a table can't miss a Release the posts saw, or the reverse.
- **`release.yml`:** the `docs` job passes the plan's queue (the PRs this run released) as `--wait-for-prs`. Manual runs of `backfill-blog-posts.yml` don't wait, as before.

### Testing

- New tests: a Release listed only on the third call (two waits, then all posts and the table row), the tables reusing the same listing, a Release that never appears (warning after the last attempt, the other posts still written), no waiting without `--wait-for-prs`, and the CLI passing the flag. Six of them, counting the updated inputs test, fail against the old script.
- All script tests: 186 passed, 1 skipped.
- `yamllint`, `actionlint` and `zizmor` are clean, and the pre-push gate passed.
