# fix(sandcastle): Open one pull request per issue instead of merging locally

- **Release tag:** `v0.0.45`
- **Source PR:** [#236](https://github.com/mpaulosky/IssueTracker/pull/236)

## PR description

### Why

This addresses the Claude Review findings on the merged #228, which committed the Sandcastle setup. Three of them are design problems with the old plan, implement, merge loop:

- **Done was decided by this run's commits.** A branch went to the merger only when `commits.length > 0` for this run. A re-planned issue whose branch already held finished work made no new commits, so it was never merged. An implementer that ran out of iterations without <code>&#60;promise&#62;COMPLETE&#60;&#47;promise&#62;</code> still had its commits merged and its issue closed.
- **The merger closed issues before anything reached GitHub.** It merged into the host checkout (which stays on `main`, where the hooks refuse commits and pushes) and then ran `gh issue close`, with no PR, checks or review.
- **Untrusted text reached agents holding `GH_TOKEN`.** Every comment and issue body on a `Sandcastle` issue went into the planner's prompt, and the implementer fetched the issue with `gh`. On a public repo anyone can comment, so injected instructions could steer agents that had an Issues-write token.

### What changed

This ports the host-side design from mpaulosky/Articles#308, without the problems that design's own review found.

- **One draft PR per issue, no merger.** `merge-prompt.md` is gone. `lib/build.mts` runs each issue in its own sandbox: implement, merge `origin/main`, run `.sandcastle/check.sh`, review, then push and open a draft PR whose body ends `Fixes #n`. The issue closes when that PR merges through the normal checks. Anything that stops (unfinished, merge conflict, failed check, rejection, failed push) gets a comment on the issue and isn't pushed.
- **Done means finished and ahead of main.** The implementer must signal completion. After that the branch is checked, reviewed and published whenever `git rev-list --count origin/main..HEAD` is above 0, so earlier finished work still gets its PR.
- **The reviewer returns a verdict.** It ends with <code>&#60;verdict&#62;&#123;&#34;approved&#34;&#44; &#34;summary&#34;&#125;&#60;&#47;verdict&#62;</code> (`lib/verdict.mts`). A missing or malformed verdict counts as a rejection.
- **Only the host talks to GitHub.** `lib/github.mts` reads issues with the host's `gh` auth and keeps only issues opened by, and comments from, an `OWNER`, `MEMBER` or `COLLABORATOR`. The agents get the issue through prompt arguments. `.env.example` no longer has `GH_TOKEN`, and `main.mts` refuses to start if `.sandcastle/.env` sets `GH_TOKEN` or `GITHUB_TOKEN`, since Sandcastle passes every key in that file into the sandbox.
- **Fixes for what Articles' review found:**
  - The host runs git with `-c core.hooksPath=/dev/null`. `core.hooksPath` is `.github/hooks`, a path inside the worktree the agents edit, so running its pre-push hook on the host would run their code outside the sandbox. CI runs the full suite, the Docker-backed tests included.
  - Each branch merges a freshly fetched `origin/main` in the sandbox before the check. On a conflict the merge is aborted and the issue gets a comment.
  - Open PRs from forks (`isCrossRepository`) neither hold an issue back nor pass for its PR.
  - Repeated planner picks are dropped (`lib/plan.mts`).
  - A PR title like `Add search .` becomes `feat: Add search`, with no trailing space.
  - After the reviewer, the host compares HEAD with the commit that passed the check, not the commits the run reported, so an amend or reset is caught. If HEAD moved, the check runs again. The host pushes that exact commit by its id, without force.
- **Branches:** existing local branches are reused alongside origin's. When origin has the branch, the local branch is created from it, or fast-forwarded to it if it's behind.
- **Host hardening (from this PR's review):**
  - Sandcastle mounts the clone's `.git` into each sandbox, writable, so an agent could write commands into `.git/config` for the host's git to run. `main.mts` records `git config --local --list` before any sandbox starts, and the host refuses to run git or `gh` once it has changed (`lib/shell.mts`). `gh` takes `--repo` from the name read at the start, not from the remotes.
  - Issue comments and PR bodies have the sandbox's secrets removed: the values `.sandcastle/.env` gives it, and anything shaped like a Claude or GitHub token.
  - "fixes #12"-style references in the reviewer's summary are rewritten as "fixes issue 12", so only the host's `Fixes #n` line closes an issue.
  - A branch that changes the files deciding what `check.sh` runs or skips (`check.sh`, `needs-docker.sh`, `discover_tests.py`, `package.json`, or a `RequiresDocker` flag) is named in a WARNING at the top of its PR.
  - The planner gets the in-review issues as open blockers, since nothing reaches main between rounds, and an issue that stopped isn't rebuilt later in the same run.
- **`.sandcastle/check.sh` (from #231) is now enforced.** The host runs it in the sandbox through `lib/check.mts`, and a passing check over uncommitted changes still fails. `check.sh`, `CODING_STANDARDS.md` and `CLAUDE.md` no longer call it advisory, and they say CI runs the Docker-backed suites. The implement and review prompts keep #231's Docker guidance.
- **`test:sandcastle`** runs `tsc --noEmit -p .sandcastle` before the tests (new `.sandcastle/tsconfig.json`, with `typescript` and `@types/node` as dev dependencies). `engines` requires Node 22.18 or later, which strips the `.mts` types. The tests now import `@ai-hero/sandcastle` and `zod`, so `.github/ci/sandcastle-tests.sh` runs `pnpm install --frozen-lockfile` first. It uses pnpm from the PATH, or corepack's when there isn't one.

#### Findings checked but not changed here

- **`branches.mts:45`, bug issues on `hotfix/`:** already fixed by #232.
- **`test:sandcastle` not run in CI:** #231 runs it from the gate and from CI's Build Solution job, through `.github/ci/sandcastle-tests.sh`.
- **Shell blocks from issue titles:** in `@ai-hero/sandcastle` 0.12.0, `substitutePromptArgs` marks the template's own `` !`…` `` blocks with `\x01` before it fills in <code>&#123;&#123;KEY&#125;&#125;</code> arguments and strips that marker from argument values. `preprocessPrompt` runs only marked blocks, so a block written in an issue title or body isn't run. A new test in `prompts.test.mts` checks that only host-made values (`BRANCH`, `BASE_BRANCH`, `TASK_ID`) appear inside the prompts' shell blocks.
